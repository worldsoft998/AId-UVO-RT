# The blackbox engine

Blackbox mode is what you can do when you are *not* allowed inside the simulator:
the same optimization loop, driven entirely by artifacts any engineer can read —
the transcript and the coverage database.

## What it controls

| Control | Mechanism |
|---|---|
| seed | `vsim -sv_seed <n>` |
| plusarg profile | `+NAME=value` from your knob inventory |
| UVM config (optional) | `+uvm_set_config_int=<comp>,<field>,<value>` |
| run length | the generated do-file's `run <time>` |
| test / top | which elaborated unit to launch |
| early abort | Ctrl-Break / SIGINT when the transcript says the run is wasted |

## The generated do-file

Per run, AId-UVO-RT writes a **simulator-only** do-file into the run directory:

```tcl
# generated by AId-UVO-RT -- simulator commands only
onfinish {
    coverage save <run>/coverage.ucdb
    quit -f
}
run 2000us
coverage save <run>/coverage.ucdb
quit -f
```

It contains no design knowledge: no signal, no class, no covergroup. If you want
your own elaboration script to run first, set `blackbox.user_do` and it is
`do`-ed instead of the `run` line.

## Real-time behaviour without internals

The transcript is tailed while the simulator writes it:

* `** Error` / `UVM_ERROR` / `** Fatal` → abort the run immediately, keep the
  partial coverage;
* assertion failures → optional abort (`abort_on_assert`);
* `sim time = ...` → simulated effort so far;
* `Total coverage: NN%` → a cheap progress signal even before the UCDB is read;
* `AIDUVRUN {...}` → a structured marker any testbench can emit if you want to
  give the agent extra context.

Aborting is a graceful interrupt (Ctrl-Break on Windows, SIGINT elsewhere) so the
simulator still runs `onfinish` and saves its coverage.

## Coverage import

```
coverage.ucdb --(vcover report -xml)--> coverage.xml --(UCIS parser)--> CoverageSnapshot
```

If the file is already XML (as the mock backend writes), it is parsed directly.

## Knobs: the user's control surface

The framework cannot invent plusargs — they are declared inside the testbench it
is not allowed to read. You declare them once:

```json
{
  "knobs": [
    { "name": "NUM_TXNS",  "kind": "plusarg_int",  "lo": 100, "hi": 2000, "step": 100 },
    { "name": "STIM_MODE", "kind": "plusarg_enum", "values": ["0", "1", "2"] },
    { "name": "ERR_RATE",  "kind": "plusarg_enum", "values": ["0", "5", "20"] }
  ]
}
```

`KnobSpace` turns that into named **profiles** (the `knob_profile` action head).
If you declare none, you get `none` and the agent explores seeds and run length
only — still useful, just less to learn.

UVM's standard `uvm_set_config_*` plusargs are supported as a knob kind, so a UVM
environment that exposes config knobs can be steered without any code change:

```json
{ "name": "env.agent::num_txns", "kind": "uvm_config_int" }
```

## Seed strategy

The `seed_mode` action head is interpreted by `SeedStrategy`:

| Mode | Seed |
|---|---|
| `sweep` | `base + run_index` (the baseline's behaviour) |
| `fresh` | uniform random |
| `resume_best` | the seed that produced the best score so far |
| `mutate_best` | best seed plus a random delta |

## Fairness note

Baseline and blackbox use **the same runner**. The only difference is that the
baseline's action is fixed to `seed_mode=sweep, profile=none`. That is deliberate:
if the baseline used a different code path, any measured difference could be an
artefact of the harness rather than of the AI.

## When blackbox is the right choice

* you have no licence to attach to the simulator's Tcl/FLI surface;
* the design is enormous and a per-quantum round trip is too expensive;
* the testbench already exposes good plusarg knobs (many do);
* you want a low-risk first deployment: no new commands, only seeds and plusargs.
